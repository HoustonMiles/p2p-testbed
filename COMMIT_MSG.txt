Mesh step 4c: peers join a running mesh (the best case)

Until now a peer waited at the rendezvous until every member was there,
and only then started its links, so however far apart peers started,
they all punched together. Now a mesh can grow while members arrive.

- peer: each link starts the moment the rendezvous introduces its member
  (onPeerInfo), up to the room's size. Members that arrive later link
  with those already running, and those link with them. Throughput
  tests still wait until the room is complete. Once it is full, or after
  -rendezvous-timeout, later members are ignored, as before.
- mesh trial: stagger_ms spaces the starts (a first, then b, c, ... each
  stagger_ms later); 0, the default, is the all-at-once worst case. The
  peers wait at the rendezvous as long as the spacing needs.
  New columns join_ms_p50 / join_ms_max: from a peer's start until its
  usable links with the members already running were ready at both ends.
- Experiments: a key of [params] may be a matrix key, so each
  configuration runs its trials with its own value (a result column, not
  a testbed setting). Configurations without one keep their IDs (all 120
  unchanged).
- p2prunner mesh: new column join_p50_ms; configurations in the
  experiment's order.
- experiments/mesh_join.toml: 8 and 16 peers, 0 / 100 / 500 / 2000 ms
  apart, realistic and mixed NATs, coast profile.

Sandbox run (no netem, 2 runs per configuration): every pair did as
RFC 4787 predicts at every spacing; realistic meshes complete. Median
join time at 16 peers: 317 ms all at once, 187 ms 100 ms apart, 169 ms
at 500 ms or more; at 8 peers about 160 ms at any spacing.

Tests: a member joining 1.5 s late, with the first two linked before it
comes (mutation-checked against waiting for the full room); spaced
commands and join times; [params] keys in the matrix.
